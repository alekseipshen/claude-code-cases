# Skill: Telegram-агент на базе Claude Code CLI

> Это инструкция-скилл. Скормите её своему AI-агенту как контекст — и он поймёт, как устроен Telegram-бот, который является полноценным агентом (твой Claude Code в кармане): работает 24/7 на внешнем сервере, держит сессии бесшовно с десктопом, использует форум-топики как отдельные проекты. Технические термины оставлены на английском намеренно.

## Что делает
Telegram-бот = тонкий мост к **Claude Code CLI**. Ты пишешь боту (текст/голос/фото/файл) — на сервере поднимается `claude` в твоём рабочем репозитории, делает работу (Read/Write/Bash/MCP), стримит прогресс обратно в чат. Это не «чат с LLM», а тот же агент, что у тебя в терминале, доступный с телефона.

## 1. Архитектура моста Telegram ↔ Claude
- **Telegram**: библиотека `python-telegram-bot` (async, Bot API, long-polling). Хендлеры на text / voice / photo / audio / document / video + commands + callback-кнопки. `concurrent_updates(True)`.
- **Claude вызывается НЕ через API, а как CLI-subprocess:**
  ```
  claude -p "<prompt>" --model <model> --output-format stream-json --verbose [--resume <id> | --continue]
  ```
  - `-p` — headless (non-interactive) режим.
  - `--output-format stream-json --verbose` — поток newline-delimited JSON событий на stdout, парсится вживую для прогресс-индикации.
  - Весь агентный цикл (tools, файлы, MCP, рассуждение) живёт **внутри** порождённого процесса `claude`, а бот лишь стримит ввод/вывод.
- Лёгкие побочные задачи (генерация названия топика, саммари сессии) — отдельный быстрый вызов `claude -p ... --model haiku` без стриминга.

## 2. Внешний сервер и запуск 24/7 (важно)
- Процесс крутится как **systemd-сервис** (`Type=simple`, `Restart=always`, логи в journal, `PYTHONUNBUFFERED=1`).
- Unit задаёт `HOME` и `PATH` (с npm-global bin, чтобы резолвился `claude`) — subprocess наследует этот env.
- **Почему отдельный сервер, а не ноутбук:** бот должен поллить Telegram и гонять Claude круглосуточно, независимо от того, открыт ли ноут. systemd даёт автостарт при загрузке и авто-рестарт при падении.
- Прод-замечание: каждый `claude`-subprocess и его shell-инструменты живут в cgroup сервиса — ставьте `MemoryMax`/`OOMScoreAdjust` на unit (рекурсивный `grep` в этом cgroup однажды утянул сервер в OOM).

## 3. Сессии: новые и старые + бесшовность с компьютером ⭐ (ядро)
Два слоя хранения:

**(а) Указатель сессий бота** — маленький JSON (`.sessions_claude.json`), ключ = **session_key**, значение:
```json
{ "resume_session_id": "<uuid>", "use_continue": false, "model": "opus" }
```
Логика сборки команды:
- есть `resume_session_id` → `--resume <id>` (предпочтительно, детерминированно)
- иначе `use_continue=true` → `--continue`
- иначе — новая сессия (без флага)

`/new` чистит `resume_session_id` **только для своего ключа**.

**(б) Захват session_id из вывода CLI:** в stream-json первым приходит событие `{"type":"system","subtype":"init","session_id":"…"}`. Бот ловит его, и после успешного прогона записывает `resume_session_id` обратно в стор. Следующее сообщение по этому ключу резюмит **ту же** сессию Claude.

**Session key:** `forum:{thread_id}` в форум-группе, иначе `chat_id` в личке. То есть **сессии раздельные по топикам** (и по чатам в DM) — каждый топик = изолированный диалог.

**Бесшовность Telegram ↔ десктоп (это и есть фишка):** Claude Code CLI сам хранит каждую сессию как JSONL-транскрипт в глобальном сторе:
```
~/.claude/projects/<workspace-path-со-слешами-замена-на-дефисы>/<session_id>.jsonl
```
Поскольку бот запускает `claude` с `cwd = тот же рабочий репозиторий`, его сессии падают в **тот же стор**, что и сессии `claude`, запущенные в этом репо из терминала/IDE. Следствия:
- `/resume` в боте читает эти `.jsonl` (свежие сверху), показывает первую реплику как ярлык, ищет по тексту и даёт выбрать кнопкой → ставит `resume_session_id`.
- **Сессия, начатая на компьютере, видна в Telegram-`/resume` и наоборот** — оба пишут в один `~/.claude/projects/<encoded-workspace>/`.
- После резюма бот ещё выстреливает one-shot «summarize what we discussed», чтобы вернуть контекст.

> Итог: бесшовность = **общий workspace cwd + общий `~/.claude` стор + session_id из stream-json + `--resume <id>`**. Никакой отдельной БД — транскрипты CLI и ЕСТЬ кросс-девайс хранилище сессий.

(Нативный аналог «из коробки» — Claude Code **Remote Control**: официальный кросс-девайс доступ к сессии, OAuth, аппрув каждого инструмента. Этот бот — самописная альтернатива с автономным исполнением.)

## 4. Суперпапка (workspace root = «второй мозг»)
- `WORKSPACE_PATH` (корень репо) передаётся как `cwd=` в каждый subprocess `claude`. Всё, что делает агент — Read/Write/Edit/Bash, доступ к MCP, чтение `CLAUDE.md` — рутится в одном репозитории.
- Так как cwd постоянный, **все сессии делят одни файлы, один проектный `CLAUDE.md`, один `.mcp.json` и одну историю `~/.claude/projects/<encoded-workspace>`**. Один workspace = один общий контекст/знания, с какой бы поверхности ты ни зашёл (топик в TG, терминал, IDE, мобильный remote-control). Кодировка «путь папки → `~/.claude/projects/<dashed-path>`» и связывает физическую папку с её историей сессий.

## 5. Топики / форум (command center)
- Бот живёт в **Telegram forum supergroup** («командный центр»). Конфиг — `forum_topics.json`: `chat_id` + map `{thread_id: "название"}` + обратный routing.
- **Маппинг:** топик (`message_thread_id`) → сессия (`forum:{thread_id}`) → опциональный инжект контекста. Каждый топик = самостоятельный проект/контекст со своей сессией Claude.
- **Инжект контекста по топику:** для известных топиков (например «Отчёты», «Google Ads», «Автоматизация») бот префиксит системный абзац, указывающий Claude на нужные доки/правила, перед самим запросом.
- **Динамические «agent»-топики:** топик с эмодзи-роботом — general-purpose. На первом сообщении после `/new` бот генерит 2-3-словный заголовок (Haiku) и **переименовывает топик** (`edit_forum_topic`), сохраняя имя в конфиг. Создал топик + кинул задачу → топик авто-подписан по содержимому.
- **Совместное владение форумом:** несколько ботов/сервисов делят один форум, каждый владеет своими `thread_id` (хендлеры early-return для чужих); проактивные отправители (n8n, мониторы) постят в свой топик. Все исходящие вызовы передают `message_thread_id`, чтобы ответ лёг в исходный топик.

## 6. Поток сообщения (пошагово)
1. **Приём:** срабатывает типизированный хендлер. Гейт доступа: отправитель = единственный разрешённый user id, иначе тихо выходим. Чужой топик → выход.
2. **Скачивание медиа** (если есть) во временный файл; лимит Bot API на скачивание — 20 MB.
3. **Debounced inbox:** сообщения по ключу `(chat_id, thread_id)` копятся ~2 сек (таймер сбрасывается на каждом новом) — альбом + подпись + дописка склеиваются в ОДИН запрос к Claude. Ранний ack «Принимаю…».
4. **На срабатывании таймера:** транскрипция аудио/голоса (внешний STT, напр. Gemini) → текст; сборка промпта; вложения отдаются **по пути** (`Прикреплённые файлы: <path>`), чтобы Claude прочитал их сам через Read tool (не инлайнить); префикс контекста топика; определение `session_key`.
5. **Запуск Claude** (`run_claude_streaming`): команда с resume/continue из стора; чистка env (см. готчи); subprocess с `cwd=WORKSPACE_PATH`.
6. **Стриминг прогресса:** читаем stdout чанками, `json.loads` каждого события; `system/init` → ловим session_id; tool-calls → человекочитаемые строки («📖 Читаю…», «⚡ $ …», «🤖 Субагент…»); финал — `result`/`message_stop`. Статус-сообщение **редактируется на месте**, не чаще 1 раза в 2.5 с.
7. **Финализация:** на успехе сохраняем `resume_session_id = session_id`.
8. **Отправка ответа** новым сообщением(ями): стрип markdown, нарезка на чанки ≤4000 символов, markdown-таблицы → PNG (headless Chromium) и отправка картинкой, отправка файлов, которые Claude создал И упомянул в финале (whitelist расширений, ≤50 MB).
9. **Чистка** временных файлов.

## 7. Готчи / важное
- **Биллинг по подписке, не по API-ключу:** перед каждым subprocess env копируется и из него удаляются `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` и `CLAUDECODE`. Снятие ключей форсит OAuth/подписку (иначе CLI молча биллит по токенам); `CLAUDECODE` снимается, чтобы CLI не думал, что он вложен в другую Claude-сессию. Критично — соседний пайплайн однажды сжёг крупную сумму, оставив ключ.
- **Таймауты:** основной стрим — потолок 900 с (15 мин), по таймауту `kill()` + частичный текст. Побочные Haiku-вызовы — 15-20 с.
- **Лимиты длины Telegram:** ответы режутся на ≤4000 символов по границам абзацев; статус держится <~3800 и ротируется в новое сообщение при переполнении лога (хард-кап 4096).
- **Rate limits:** правки статуса не чаще 1/2.5 с; `RetryAfter` ловится и пережидается; `BadRequest`/`TimedOut` на правках глотаются.
- **Медиа:** вход ≤20 MB (Bot API download), выход ≤50 MB (Telegram send), иначе вежливое «слишком большой».
- **Конкурентность:** `concurrent_updates(True)` + per-(chat,thread) debounce inbox + `asyncio.Lock` на ключ сериализуют пачку сообщений в один прогон.
- **Права бота в форуме:** админ с правом управлять топиками (`edit_forum_topic`/`create_forum_topic`) и постить в конкретные `message_thread_id`.
- **Состояние:** durable — только `.sessions_claude.json` (resume id + model + флаги) и `forum_topics.json` (thread↔name); реальные транскрипты — в `~/.claude/projects/<encoded-workspace>/*.jsonl`.
- **Доступ:** single-tenant — один разрешённый user id проверяется в каждом хендлере и callback (не multi-user ACL).

## Что нужно (аккаунты и env — только имена)
- Telegram **Bot token** (`@BotFather`); бот добавлен админом в форум-супергруппу.
- **Claude Code CLI** установлен на сервере + **подписка Claude** (OAuth-логин в CLI). API-ключ держать НЕ в env процесса (иначе слетит на API-биллинг).
- STT-провайдер для голоса (например `GEMINI_API_KEY` / любой Whisper) — опционально.
- Сервер с systemd; рабочий репозиторий (workspace) с `CLAUDE.md` и `.mcp.json`.
- Python: `python-telegram-bot`, STT-SDK, headless Chromium (если нужен рендер таблиц в PNG).

## Стек одной строкой
`python-telegram-bot (long-polling) → debounced inbox → claude -p --output-format stream-json --resume <id> (cwd=workspace, env без ANTHROPIC_API_KEY) → парсинг событий → правка статуса в TG`, сессии = `~/.claude` JSONL (общие с десктопом), топики форума = изолированные проекты, всё под systemd 24/7.
